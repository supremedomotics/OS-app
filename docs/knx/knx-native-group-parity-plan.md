# Plan — native group read/write and telegram-feedback parity with the legacy driver

2026-10-18 · Written as a plan after the health vertical slice (`knx-device-health-design.md` §8); **deliverables 1–5 below are now implemented and simulator-tested** (status and results in §6–§9). Goal: a native implementation of the production driver's bus seam, proven against the legacy driver's own tests, still behind the feature flag. **Evidence level of everything below: simulator-tested (S) and unit-tested (U); specification-verified (V) only where stated; real-hardware-tested (H): none.**

## 1. The seam (verified in code)
`KnxProtocolDriver` (`services/protocols/src/knx-driver.ts`) reaches the bus only through `KnxConnection` (lines 37-48):
`connect()` · `disconnect()` · `write(groupAddress: string, value: KnxValue, dpt: string)` · `observe(groupAddress, dpt, handler(value)): unsubscribe`.
Its 121 tests (`knx-driver.test.ts`) drive the driver with a **fake** `KnxConnection`; they never touch `knxultimate`. Everything above the seam (command/feedback attribution, HVAC multi-GA roles, DPT 20.102/20.105/1.100/22.101/222.100 handling, provenance `commanded` vs `observed`) is therefore independent of the transport and stays untouched. Parity means: **a native class implementing `KnxConnection` behaves like `wrapKnxUltimate` for everything the driver can observe**, with the deliberate deviations already documented (D1 22.101 raw number, D2 222.100 lowercase keys, D3 invalid 0x7FFF).

## 2. Deliverables (in order, each independently testable) — status in the right-hand tag
1. **`NativeTelegramBus`** (`native/telegram-bus.ts`): multi-subscriber per group address, **per-handle unsubscribe** (fixes legacy D4 in the provider; the production wrapper already does per-observer removal), bounded history, source address kept on every telegram, delivery isolation (a throwing handler never affects others), telegram stream fed by `KnxTunnelClient.onTelegram`. The health monitor becomes one more subscriber (replacing its direct `onTelegram` listener). — **DONE** (`native/telegram-bus.ts`, 24 tests; one deliberate change: no separate `onTelegram`-fed health listener yet — the health monitor attaches through the `onLinkUp` hook)
2. **`NativeKnxConnection implements KnxConnection`** (`native/knx-connection.ts`): `connect()` = supervised fresh tunnel (reuse the `ConnectionManager` wiring proven in `health-service.ts`, extracted rather than copied); `write()` = encode via `native/dpt.ts` + `sendGroup(write)`; `observe()` = bus subscription + DPT decode (`native/dpt.ts`), responses **and** writes count as feedback exactly like the wrapper (reads are ignored — already true in `cemi.ts`). — **DONE** (`native/knx-connection.ts` + `supervised-tunnel.ts`; reconnect decision in `knx-reconnect-ownership.md`)
3. **Read facade** `read(ga)` (GroupValueRead trigger for state sync) on the same class, used by `SupremeKnxDriver.syncAll`; shares the health monitor's budget so sync and probing cannot overload the bus. — **DONE as `read()` on the class** (response correlation by group address only; not called by the driver; no budget sharing with the health monitor yet)
4. **Contract suite** `knx-connection.contract.test.ts`: one table of behaviours, executed against (a) the fake used by the legacy tests and (b) `NativeKnxConnection` over the simulator, so both implementations are held to the same observable contract. Cases: write encodes the right bytes per DPT; observe receives writes and responses, not reads; two observers on one GA, unsubscribing one leaves the other; unsubscribe is idempotent; handler exceptions isolated; reconnect restores subscriptions without duplicates; connect failure leaves no listener/socket/timer (legacy leak regression); write while disconnected fails visibly; invalid GA/DPT rejected before any frame is built. — **DONE** (`native/simulator/knx-connection.contract.ts`, run by `knx-connection.contract.test.ts` against legacy and native)
5. **Driver parity run**: parametrise `knx-driver.test.ts`'s fake-bus fixture so the SAME 121 tests run with `KnxProtocolDriver({ connection: new NativeKnxConnection(...simulator...) })`. The tests that depend on library-specific decoding (the three intentional deviations) get explicit paired expectations ("legacy: …, native: …") instead of silent edits. — **DONE** (`KNX_DRIVER_BUS=native`; the 121 tests unchanged)
6. **Differential cases** that stay valid only while `knxultimate` is installed (`dpt-differential.test.ts` already auto-skips when it is gone). — unchanged (`dpt-differential.test.ts`)
7. **Shadow mode** (still no cutover): flag-gated, runs `NativeKnxConnection` read-only alongside the legacy connection on a non-customer installation, compares observed values per GA and reports divergences through the diagnostics service. — **DESIGN ONLY** (`knx-shadow-mode-design.md`)

## 3. Out of scope for that milestone
Secure (blocked), routing (not used by legacy), individually-addressed frames, ETS-driven bindings changes, production registration, removal of `knxultimate`.

## 4. Exit criteria
Contract suite green for both implementations; the 121 driver tests green on the native connection with the three documented deviations asserted explicitly; no new timer/socket/listener after 100 connect/disconnect cycles; no change to `knx-driver.ts` behaviour for connections without a link state (superseded in part on 2026-10-19: the driver gained optional link-state reporting, an honest `isConnected()` and in-flight `connect()` cancellation — §10.3, simulator-tested, not hardware-tested); hardware-in-the-loop checklist drafted (gate G5) but **not** claimed.

## 5. Risks to watch
Handler ordering and re-entrancy differences from the library (same-tick delivery); string GA canonicalisation (`1/1/1` vs raw); DPT decode differences beyond D1–D3 found only by the differential suite; the legacy driver's own auto-retry in the gateway (60 s) interacting with the supervisor's backoff — decide a single owner of reconnects before wiring.

### 6.1 The 121 driver tests on the native connection — what "pass" means here
* All 121 pass **unchanged** (assertions untouched; only the bus fixture is selected by `KNX_DRIVER_BUS`). Default runs still use the in-memory fake: 121/121.
* **60 tests (64 counting the four below, which also alias — measured 2026-10-19, see `knx-native-parity-evidence.md`) use synthetic group addresses with a main group above 31** (e.g. `92/1/3`); KNX three-level addressing has a 5-bit main group, so the native connection correctly rejects them (`invalid_address`). The harness maps each to a distinct valid address in main group 31 and maps back in `writes`. This is a property of the fixtures, not of the driver — but it means those 60 tests do **not** exercise address parsing, and production would reject such a binding where the legacy library silently never matches it.
* **`push()` is synchronous** (the legacy tests assert right after it), so it encodes the value, builds and re-parses a real cEMI L_Data.ind and publishes into the bus: everything but the UDP hop. **Writes are real**: `writes` is what the virtual gateway received over the tunnel, and the harness fails a test if the wire value differs from the request.
* **4 tests pass because the native transport dropped a telegram the fake delivered**: `Phase 3.3C-3 E` (heatCool value 7 is a 6-bit short value on the wire → refused as `bad_payload` before the driver sees it) and the three `Phase 3.3D-FIX — duplicate HVAC GA assignment` tests (two observers share one GA with different DPTs; one decode fails). Their assertions hold either way.
* The fake delivers a pushed value only to the **last-registered** observer on a GA; the legacy wrapper and the native bus deliver to **all**. The native run is therefore closer to production than the fake — and shows the legacy suite never asserted fan-out.
* Intermediate failures while building the harness (60 from address validity, 10 from value representation) were all harness issues; **no native defect was found by the 121 tests**, and none was hidden or loosened.

## 7. The three known decoding differences — classification

Evidence for the legacy side is `knxultimate` 6.0.1 library output (dptlib run directly) and the production codec source; **no KNX Datapoint Types specification text is in the repository** (see the scope audit, requirement 7), so nothing below is *specification-verified (V)*.

| # | Difference | Legacy (library) | Native | Classification | Evidence / confidence |
|---|---|---|---|---|---|
| D1 | DPT 22.101 `0x0103` | object `{Fault, StatusEcoH, HeatCoolMode, …}` | number `259` | **Intentional; the legacy path has a compatibility defect.** `decodeHvacStatus` does `Number(value)`, so the object form yields `NaN → null`: HVAC status never populates in production. The bit-field object is *also* a legitimate reading of a flag type; the point is that it is not what the production decoder consumes. | **[Certain]** for the incompatibility (library output + `knx-codec.ts`). **[Guessing]** that the bit order of the native raw number matches the spec: `decodeHvacStatus`'s bit map is itself unverified against the DPT text. |
| D2 | DPT 222.100 `0c1a 0c9a 0b00` | `{Comfort:21, Standby:23.56, Economy:15.36}` | `{comfort:21, standby:23.56, economy:15.36}` | **Intentional.** Values are identical; key case is an API convention (`KnxSetpoints`/`isKnxSetpoints` require lowercase), not something the DPT defines. Legacy keys make HVAC setpoints decode to `null` in production. | **[Certain]** (both sides run in the contract suite). Field order comfort/standby/economy matches the library; spec order unverified. |
| D3 | DPT 9.001 `0x7FFF` | `670760.96` delivered as a reading | refused, counted (`invalid_data`), previous good value kept; a later valid value is delivered | **Specification-intended (to be confirmed against the DPT text) and a legacy defect.** The project's own driver already treats `670760.96` as invalid inside DPT 222.100 fields, so the legacy path is internally inconsistent: a plain DPT 9 sensor would publish 670760.96 °C. Inside DPT 222.100 native keeps the same sentinel as the library (`F16_INVALID_VALUE`) so field-level invalidation in `decodeHvacSetpoints` is unchanged. | **[Likely]** that 0x7FFF is the DPT 9 invalid code (library constant + project code agree; spec not held). **[Certain]** about the observable difference. |

Other documented native-stricter differences remain in `dpt-differential.test.ts` (DPT 1 non-0/1 octet, DPT 17 reserved bits, DPT 14 non-finite, encode rounding, 5.003 half-steps); the 121 driver tests do not exercise them (they inject decoded values).

## 10. Corrective milestone after d9a113a (2026-10-19) — simulator-tested; NOT committed, NOT registered, NOT hardware-tested

Triggered by a review of d9a113a. Four items; results and evidence levels:

**10.1 Single-slot race (defect found by a test, then fixed).** The existing "single-slot" tests ran on the simulator's default **four**-slot gateway, which hides the race. New tests (`single-slot.test.ts`, `maxTunnels: 1`, delayed CONNECT_RESPONSE) reproduce: predecessor's CONNECT_REQUEST answered (only slot allocated), client has no response, predecessor replaced and its caller released, replacement connects. **Before the fix the replacement was refused (`NO_MORE_CONNECTIONS`) at t = 51 ms** (`refusedConnects = 1`). Fix: `SupervisedTunnel.quiesced(timeoutMs)` (bounded wait for unfinished handshakes *and* the orderly close of a discarded tunnel; never cancels anything, never part of `disconnect()`); `createSingleSlotConnectionFactory` waits on it (default bound 15 s = tunnel connect + disconnect timeouts; option `settleTimeoutMs`) after `previous.disconnect()`, which still releases the old caller immediately (asserted < 100 ms while the response arrives at 1 500 ms). After the fix: replacement connects at ≥ 1 500 ms, `refusedConnects = 0`, peak gateway channels = 1, the predecessor's channel closed by an orderly DISCONNECT (`disconnects = 1`, `idleDrops = 0`). Other cases: delayed refusal (no slot taken → still one tunnel); **lost CONNECT_RESPONSE** (gateway slot orphaned for its 120 s idle timeout and *nobody can close it* — the protocol gives no way without the channel id; the replacement fails retryably, the caller's retry is refused again until the gateway drops the orphan, then connects; this is a protocol limit, hardware item H-2, not a bug fixed here); settlement **bounded** (response later than `settleTimeoutMs`: replacement released at the bound, refused retryably, late tunnel still closed orderly, retry succeeds); shutdown while waiting (nothing left behind). Mutation: removing the wait makes the late-response test fail.

**10.2 Health ownership — integrated (S), not wired.** `KnxHealthService` keeps its own tunnel and stays a standalone simulator composition (documented as not for production). New `health/native-health-attachment.ts` (`NativeKnxHealthAttachment`) uses **only** `NativeKnxConnection`'s `onLinkUp` hook and opens no tunnel. Ownership: tunnel/reconnect = `SupervisedTunnel`; telegram subscription = the attachment (one wildcard subscription, removed by the hook's cleanup before any next link-up); monitor + its evidence + its per-minute budget = the attachment, for its whole life; monitor timers = the monitor (start idempotent, stop on link-down); read budget = the connection. New `native/read-budget.ts`: **one `ReadBudget` per connection shared by `read()` and the health port** (concurrency, per-minute window, health capped at `healthShare` = 25 % so probes cannot starve a sync; defaults preserve `read()`'s old 64-concurrent cap, plus 600/min). The hook context gained `reads: ReadOnlyBusPort` (GroupValueRead only, **refused on an observe-only connection**, no write method; the raw `tunnel` stays in the context for the existing hook tests but the attachment ignores it). Tests (`native-health-attachment.test.ts`, 7, one-slot gateway, full driver → connection → budget → attachment → monitor path): one channel and zero refusals, tunnel sends only reads, observe-only puts nothing on the line, three outages with exactly one subscription/loop/tunnel after each recovery, sync + probes share the budget, disconnect releases everything, replacement works. Mutations killed: health bypassing the budget; attachment not unsubscribing. Known limits: the hook cleanup carries no close reason, so after link loss the gateway reachability is `unknown` (the standalone service distinguishes `unreachable`); the monitor counts a budget-refused read in `load.readsSent` (it increments before the bus call) — cosmetic, unchanged; `SupremeKnxDriver.syncAll` still does not call `read()`.

**10.3 Driver-facing link state — smallest backward-compatible change (`knx-driver.ts`).** `KnxConnection` gained an optional `readonly linkState?: "idle"|"connecting"|"up"|"recovering"|"closed"` (the native connection already had it; fakes and the legacy wrapper have none and are treated as "up" while they exist — unchanged). `KnxProtocolDriver.connectionState()` → `disconnected | connecting | connected | recovering`; `isConnected()` is now `connectionState() === "connected"` (**the driver no longer reports healthy merely because a connection object exists**). No observer/bindings duplication is possible by construction: bindings subscribe once per connection on the bus that outlives tunnels (tested over 3 outages: subscriptions unchanged, one event per telegram, one connection object). `connect()` while `recovering` is a deliberate no-op (the supervisor owns recovery; a second tunnel would compete for the slot); a connection that reports `closed` (e.g. replaced by the single-slot factory) is dropped and its observers released so the caller's retry builds a new one. **`disconnect()` during an in-flight connect** now bumps an epoch, cancels the pending connection, rejects the caller at once (`knx: disconnected during connect`) *even if the connection's own `connect()` never settles* (the legacy wrapper waits for an event — checked by reading `wrapKnxUltimate`, not run against the real library), and closes a connection the factory returns late; before, the replaced driver went live after being disconnected. A failed first connect still leaves `conn = null` and is retryable (tested on the fake and on the native connection against a refusing gateway). One pre-existing test that *documented* the old hazard ("a replaced driver whose connect was still in flight leaves a second tunnel") was rewritten to assert the new behaviour — it is the only existing test changed; the 121 driver tests are untouched and pass on both buses. Evidence S/U; the legacy `knxultimate` wrapper's mid-connect `Disconnect()` is **not** hardware- or library-tested.

**10.4 Parity evidence.** New `knx-native-parity-evidence.md` (per-group classification of the 64 aliased tests and the 4 drop-passing tests: what each proves and does not) and `native/driver-valid-address.test.ts` (6 tests, valid addresses, status over the full wire path). Corrected count: 64 aliased in total (60 + the 4), 92 of 121 tests use a bus. DPT differential suite: 39/39, differences D1–D3 and the strictness set still asserted explicitly; nothing is called specification-verified.

**Not claimed:** hardware validation of anything; that the legacy wrapper behaves as read; that `NativeKnxHealthAttachment`'s thresholds suit real devices; gateway KNX e2e (still unloadable in this sandbox).

## 11. D7/D8 decision, health factory, real-wrapper cancellation (2026-10-20) — simulator/loopback only; NOT hardware-tested

**State semantics (verified in `knx-driver.ts`, unchanged):** a command is announced as `commanded` and never stored (there is **no optimistic update**); only a telegram on the *declared* status address — write or response from the bus — becomes `observed` state, and identical repeats are de-duplicated by `record()`; a binding with no declared feedback observes nothing. **D7 (command echo):** the legacy wrapper ignored the library's `echoed` flag, so with `feedbackOnCommandAddress` the client's own transmission was recorded as *observed* state. **Decision:** `wrapKnxUltimate` now skips an indication only when the library positively flags it `echoed === true` (KNXClient.js 6.0.1 sets it on every own-transmission path and `false` on every received path — source reading, not a live client). **D8:** an indication whose `npdu.isGroupRead === true` is skipped too (a read request's `dataValue` decoded as 0/false). Anything the library does not flag is delivered as before — no useful telegram is dropped. **Behavioural consequence (accepted by the default design direction, owner may revisit):** a shared-GA device now shows observed state only when something genuinely reports, never from the echo. **Not decided, no normative text held:** whether a real gateway relays a tunnel's own frame back to it, and which source address a shared-GA feedback may be attributed to — no origin filter was invented. Tests: `state-semantics.test.ts` (10, both implementations through `KnxProtocolDriver`: command, echo on shared GA, independent write, response, read request, duplicates, no-feedback), contract D7/D8 now assert both sides equal; reverting the echo filter fails the legacy test.

**Health factory/lifecycle:** `health/native-health-factory.ts` (`createNativeConnectionWithHealth`) creates one connection + one attachment, refuses a caller `onLinkUp`, and `dispose()` (final, idempotent) disconnects the connection then disposes the attachment. The attachment gained `dispose()` and token-identified cleanups, so a stale cleanup (older link, or a misuse sharing one attachment between connections) cannot tear down a newer link. Owner of the pair = the caller of the (future) production factory; replacement = a new pair through `createSingleSlotConnectionFactory` (predecessor cleaned up by its link-down). Not wired into bootstrap. Tests `native-health-factory.test.ts` (7): failed start, dispose mid-connect, three reconnects, shutdown/idempotence/no re-attach, single-slot replacement, shared-attachment misuse. Mutations (token check, attachment dispose) detected. Legacy connections have no link state and never reach this code.

**Real `knxultimate` wrapper, mid-connect `Disconnect()`** (`real-wrapper-cancel.test.ts`, 3 tests; real library 6.0.1 + real loopback UDP sockets + a minimal in-process fake gateway; real timers, ~1 s library delay before the first CONNECT_REQUEST): **(1) confirmed finding:** after `Disconnect()` mid-connect the wrapper's own `connect()` promise never settles and its two listeners stay on the abandoned client. **(2)** through `KnxProtocolDriver` the waiting caller is released within 500 ms, the driver stays disconnected, no UDP socket or timer remains, and a subsequent `connect()` on a fresh client succeeds. **(3)** a CONNECT_RESPONSE arriving 1.5 s after the cancellation cannot activate the driver. Without the driver's cancellation race (mutation) two of these hang for the full timeout — the change is necessary for the legacy path. **Limits:** not a real gateway; the fake allocated a channel the library never learned about, so no DISCONNECT_REQUEST is sent (the H-2 orphan on a real one-slot gateway); NAT, firmware behaviour and routing mode are untested.
